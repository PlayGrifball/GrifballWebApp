# Developer setup

How to build and run GrifballWebApp on your own machine. For how the backend is put together, see
[architecture.md](architecture.md); for the database, [database.md](database.md).

## Tools

- **[.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)**, which comes with Visual Studio 2026 if you
  install that.
- **An editor.**
  - [Visual Studio 2026](https://visualstudio.microsoft.com/downloads/) (Community is enough) with the
    "ASP.NET and web development" workload: the easiest way to run and debug the backend, and fine for the frontend.
  - [Visual Studio Code](https://code.visualstudio.com/download): recommended for the frontend. Opening
    `grifballwebapp.client` prompts for its recommended extensions ([extensions.json](../grifballwebapp.client/.vscode/extensions.json)).
    It works for the backend too, with `dotnet watch run --project GrifballWebApp.Server` or a launch configuration.
- **[Node.js](https://nodejs.org/)**: the version the client image is built with is in
  [grifballwebapp.client/Dockerfile](../grifballwebapp.client/Dockerfile); any version
  [Angular supports](https://angular.dev/reference/versions) works. A version manager
  ([nvm-windows](https://github.com/coreybutler/nvm-windows/releases), [nvm](https://github.com/nvm-sh/nvm)) makes
  switching easy.
- **A database.** Either [Docker](https://www.docker.com/) for the compose file's SQL Server (below), or
  [SQL Server 2022 Developer](https://www.microsoft.com/sql-server/sql-server-downloads) installed locally, or
  PostgreSQL, or nothing at all with SQLite ([sqlite.md](sqlite.md)).
  [SSMS](https://learn.microsoft.com/ssms/install/install) is handy for looking at a SQL Server database.
- **Entity Framework Core tools**, for migrations: `dotnet tool install --global dotnet-ef --version 10.*`
  ([docs](https://learn.microsoft.com/ef/core/cli/dotnet)).

Then restore everything:
```sh
dotnet tool restore
dotnet restore
cd grifballwebapp.client
npm ci --force
```
The Angular CLI comes with the client's packages: run it as `npx ng ...` or through the `npm run` scripts, rather than
a global install.

## Database

The compose file has a SQL Server for development, on `localhost,5434`:
```sh
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d sqlserver
```
Its connection string (user `sa`, password `Pass@word`) goes in user secrets:
```json
"ConnectionStrings:GrifballWebApp": "Server=localhost,5434;Database=GrifballWebApp;Encrypt=False;User Id=sa;Password=Pass@word;"
```
`docker-compose.local.yml` keeps its data in a named volume. The base file also binds a Windows backup folder
(`C:\Program Files\Microsoft SQL Server\...\Backup`); on Linux or macOS, drop that bind or point it at a folder you have.

For Postgres or SQLite, set `Database:Provider` as in [database.md](database.md#providers).

### Running without credentials

With `Preview:Enabled=true` (the mode PR previews run in) the app skips the Discord bot's sign-in, OAuth secrets and
Halo Infinite keys, and creates two smoke-test users, `admin` and `player`. It's the quickest way to try a change
locally. On Windows, the `start-env` agent skill's scripts ([.agents/skills/start-env](../.agents/skills/start-env/SKILL.md))
start the database, backend and client this way in one command.

### Halo Infinite
The app reads match results from Halo Infinite with [Grunt](https://github.com/PlayGrifball/grunt), in one of two modes,
set by `HaloInfinite:Mode`:

- **`Gateway`** (the default, and what every deployed environment and PR preview uses): every Halo call goes through
  the Halo gateway (Grunt's `Grunt.Gateway.Host`), which holds the one signed-in Halo account for all environments. The
  app needs only `HaloGateway:BaseUrl` (default `http://halo-gateway.halo-gateway.svc:8080/`, the gateway inside the
  cluster) and its own `HaloGateway:ApiKey` (a secret, sent as `X-Api-Key`). Optional: `HaloGateway:AdminUrl` (default
  `https://grunt.grifball.xyz/admin`, the gateway's admin page, where its Halo account is signed in) and
  `HaloGateway:Retry` (the client's transport retries, e.g. `MaxAttempts`).
- **`Direct`**: the app signs in to Halo itself, as it did before the gateway, with its own Microsoft app
  (`ClientConfiguration:ClientId`, `ClientSecret`, `RedirectUrl`), and keeps the tokens (`tokens.json`,
  `AccountAuthorization.txt`) in its working directory.

Locally, outside the cluster, the gateway's Service address does not resolve. Either point `HaloGateway:BaseUrl` at a
gateway you can reach (e.g. `kubectl port-forward -n halo-gateway svc/halo-gateway 8080:8080` and
`http://localhost:8080/`) with an API key the gateway knows, or use Direct mode with your own Microsoft app, in user
secrets as above. An unknown mode or a gateway URL that isn't an absolute http(s) URL stops the app at startup, naming
the setting. Without either, the app still runs; only the Halo features (match imports, gamertag lookups) fail.

The **Infinite Client** page (`/infiniteclient`, sysadmins) shows which mode is active:

- Gateway: the gateway's status from a fresh check (`GET /api/halo/status`): whether the gateway answered, its Halo
  account's status (Healthy, or Degraded when it has to be signed in again), what a test call (one match's stats)
  through it answered, and whether this environment has an API key. The sign-in code and Delete Tokens controls are
  hidden: the account is signed in centrally on the gateway's admin page, which the page links to. `POST /api/halo/auth-code` and
  `POST /api/halo/tokens/delete` answer 409 Conflict in this mode.
- Direct: check status, open the Microsoft sign-in link it gives when signed out, and paste the code from the redirect;
  Delete Tokens clears the stored tokens.

The `halo_infinite` health check follows the mode: Direct makes the test call through the app's own sign-in; Gateway
needs the test call through the gateway to succeed and the gateway's Halo account to be Healthy. Either way it is only
ever Healthy or Degraded, never Unhealthy, and not part of readiness, so Halo never takes the site out of service.

## Running the app

1. Start the frontend: in `grifballwebapp.client`, `npm start`. It serves [https://localhost:4200](https://localhost:4200)
   with the ASP.NET development certificate (`dotnet dev-certs https --trust` if the browser doesn't trust it).
2. Start the backend: open `GrifballWebApp.slnx` in Visual Studio, make sure `GrifballWebApp.Server` is the startup
   project (in bold in Solution Explorer), pick the `https` launch profile and press F5. Or, from the command line,
   `dotnet run --project GrifballWebApp.Server --launch-profile https`.
3. The API answers at [https://localhost:7210](https://localhost:7210), with Swagger at
   [/swagger](https://localhost:7210/swagger) and the health check at [/health](https://localhost:7210/health).

The backend starts the frontend itself (the SPA proxy) when it isn't already running, but running it yourself first,
as above, avoids trouble with that.

## Tests and checks

- Backend: `dotnet test`. Unit test projects need nothing else; `GrifballWebApp.Integration.Test` starts its database
  servers with Testcontainers, so it needs Docker (`GRIF_TEST_DATABASE` picks SQL Server, Postgres or SQLite). Where
  each kind of test goes: [ci-cd/dotnet-tests.md](ci-cd/dotnet-tests.md). Coverage: [code-coverage.md](code-coverage.md).
- Frontend: in `grifballwebapp.client`, `npm test` (watch) or `npm run test:ci`, and `npm run lint` (ESLint plus the
  feature boundaries in [frontend.md](frontend.md)). More in [frontend-testing.md](frontend-testing.md).
- The clients in `grifballwebapp.client/src/generated` are generated from the server, and CI fails when they're stale:
  - **API** (`src/generated/api`), from `grifballwebapp.client/openapi.json`. After changing an endpoint, update that
    file (run the test `OpenApiDocument_Should_EqualTheOneTheClientIsGeneratedFrom` with `GRIF_UPDATE_OPENAPI=1`, or
    take it from the failed run's test results), then `npm run generate:api`.
  - **SignalR** (`src/generated/signalr`), from the hubs: the steps are in the `typed-signalr` job of
    [dotnet-tests.yml](../.github/workflows/dotnet-tests.yml), whose artifact is the up-to-date folder when it fails.
